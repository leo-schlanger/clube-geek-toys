## 2. Base de dados

### 🔴 `ensureSchema()` era um `try` único sobre 460 linhas de DDL

O bloco roda no boot da API e mantém o schema alinhado com o código deployado —
padrão pragmático e bom para o tamanho do projeto. O problema era o
enquadramento: **um único `try/catch` em volta de tudo**.

| Se a etapa 12 falha…  | Antes                       | Depois                      |
| --------------------- | --------------------------- | --------------------------- |
| Etapas 13–18          | nunca rodavam               | rodam                       |
| API                   | servia tráfego normal       | serve tráfego normal        |
| `/health`             | `ok`                        | `degraded`                  |
| Sinal para o operador | 1 linha de log do container | `/health` + deploy vermelho |

Um schema pela metade em produção só apareceria quando uma tela quebrasse — e
nesse ponto o rastro já teria sumido do log.

**Corrigido:** as 18 etapas viraram entradas nomeadas de um array, cada uma com
seu próprio `try`. Uma falha isolada não cancela as outras, o estado fica em
`getSchemaState()`, e é exposto:

- `GET /health` → `schema.status` (`pending` | `ok` | `degraded`) + contagem
- `GET /logs/schema` (admin) → qual etapa falhou e por quê
- `deploy.yml` → aguarda sair de `pending` e **falha o deploy** se vier `degraded`

O nome da tabela/coluna que quebrou não vai no `/health` público — é informação
de dentro.

> **O DDL não mudou.** A refatoração foi verificada comparando os 113 statements
> SQL antes e depois: idênticos, byte a byte.

**Confirmado em produção** no deploy de 16/08 11:03 — o `ensureSchema`
refatorado rodou contra o Postgres real e o health check do CI leu:

```json
{
  "status": "ok",
  "database": "connected",
  "schema": {
    "status": "ok",
    "ranAt": "2026-08-16T11:03:06.175Z",
    "failedSteps": 0,
    "totalSteps": 18
  }
}
```

São **18** etapas e não 19 porque a Wave 2.5 era só um comentário (a tabela
`settings` já vem do `schema.sql`) e não virou etapa. As migrations seguem indo
até a 019.

Cobertura: 5 testes em `ensure-schema.test.ts`. O que trava a regressão é este —
com o `try` único, o contador para em 3:

```
expect(calls).toBeGreaterThan(50)   // etapa 3 falha, as demais seguem
```

### O que está bem e merece registro

| Verificação                     | Resultado                                                  |
| ------------------------------- | ---------------------------------------------------------- |
| Índices                         | 113 statements; todos os filtros quentes cobertos          |
| `ORDER BY` dinâmico             | whitelist em `orderBySql()` — sem interpolação de string   |
| Agregação de linhas no checkout | soma por `productId::variantId` antes de checar estoque    |
| Desconto                        | sempre recalculado no servidor; cliente manda só id + qtd  |
| Frete                           | `quoteToken` assinado com HMAC e expiração                 |
| Transações                      | `BEGIN`/`COMMIT` com `FOR UPDATE` nos produtos e variações |

## 3. Estrutura

### 🔴 A cobertura não media o backend

`vitest.config.ts` tinha:

```js
include: ["src/**/*.{ts,tsx}", "server/api/src/utils/**/*.{ts}"];
```

Ou seja: os **74% do TODO eram do front**, mais 3 arquivos de util. Medido com o
backend incluído:

| Área                       | Cobertura |
| -------------------------- | --------- |
| `server/api/src` (total)   | **7,15%** |
| `src/routes` (23 arquivos) | **0%**    |
| `order.service.ts` (840 l) | **0%**    |
| `webhook.service.ts` (569) | **0%**    |
| `payment.service.ts` (521) | **0%**    |
| `stock.service.ts` (409)   | **0%**    |

A métrica existia, estava verde, e não olhava para as 10 mil linhas que decidem
quanto o cliente paga e quanto estoque sai.

**Corrigido:** `include` passa a cobrir `server/api/src/**`.

E aí apareceu o segundo problema, que eu não esperava: **o número do front
também estava errado**, e para pior. Medido na suíte completa de 16/08:

| Área             | stmts      | lines  | funcs  | branches |
| ---------------- | ---------- | ------ | ------ | -------- |
| `src/**`         | **67,55%** | 69,31% | 64,94% | 64,18%   |
| `server/api/src` | **11,80%** | 11,78% | 9,07%  | 10,59%   |
| total            | 49,23%     | 49,59% | 53,29% | 49,90%   |

Os 74% do TODO eram de **10/08**. Nos seis dias seguintes entraram variações,
estoque, vídeos, perguntas, galeria e atacado — mais rápido que os testes — e a
cobertura do front caiu ~6,5 pontos. Como o threshold global era 70%, isso
significa que **`npm run test:coverage` já estava vermelho antes deste checkup**.
Ninguém tinha visto porque a run completa leva ~26 minutos e não está no CI.

Os thresholds agora são o **valor medido**, por área: catraca contra regressão,
não meta. A meta continua 70% dos dois lados. Pôr 70% num piso que o código não
alcança mantém a trava vermelha — e trava que vive vermelha é trava que alguém
desliga, que é literalmente o que já tinha acontecido aqui.

### Testes do checkout — 0 → 25

`order.service.test.ts` cobre, em ordem de prejuízo:

1. Preço vem do banco, nunca do cliente
2. Membro (15%) e atacado (25%) **não** empilham
3. Frete nunca entra no desconto
4. Linhas repetidas do mesmo SKU somam antes da checagem de estoque
5. Crédito de loja não deixa o total negativo
6. Variação: SKU obrigatório, SKU de outro produto recusado, estoque do SKU
7. Atacado: login, CNPJ aprovado, CNPJ conferido, produto liberado, qtd. mínima
8. `ROLLBACK` em qualquer falha de linha

**Validados por mutação**, não só por passarem. Três regressões foram plantadas
no `order.service.ts` e os testes as pegaram:

| Mutação plantada                       | Teste que quebrou               |
| -------------------------------------- | ------------------------------- |
| membro passa a empilhar com atacado    | "atacado usa 25% e NÃO empilha" |
| desconto passa a incidir sobre o frete | "nunca sobre o frete"           |
| agregação por linha some (oversell)    | "soma linhas repetidas"         |

> Nota de método: as duas primeiras mutações que tentei eram no-ops matemáticos
> (`a - d + f` vs `(a + f) - d`) e passaram — o código é mais defensivo do que
> parecia. Só a terceira leva de mutações foi conclusiva.

### 🔴 `npm run build` estava quebrado — e o CI não usava

`npm run build` é `tsc -b && vite build`. Falhava com **154 erros de tipo**. O
`deploy.yml` rodava `npx vite build`, que transpila sem checar tipo: **erro de
tipo em código de produção nunca barrou um deploy neste projeto.**

Os 40 erros em código de produção foram corrigidos — e dois eram bugs de verdade,
não ruído de tipagem:

| Arquivo               | O que o compilador achou                                                                                                                                                                                 |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ImageCropDialog.tsx` | `sizeMode` iniciava com a **string** `'1200'`; a UI compara com o **número** `1200`. Nenhum chip de tamanho aparecia selecionado ao abrir, e `outputSpec()` mandava texto para a conta de redimensionar. |
| `ImageCropDialog.tsx` | `clampedPan` devolvia `{x,y}` antes da imagem carregar, e o consumidor lia `.panX`/`.panY` → `left`/`top` em `NaN` no primeiro render.                                                                   |
| `types/index.ts`      | `activatedAt` e `activatedByPayment` não existiam no tipo `Member`, mas o `updateMemberSchema` do backend já os aceitava desde 10/08. Os dois lados voltaram a concordar.                                |
| `AuthContext.tsx`     | `result.data` de `/auth/login` era `unknown` e ia direto para o destructuring — sem checagem de resposta vazia.                                                                                          |
| `subscriptions.ts`    | `status` cru da API atribuído a `SubscriptionStatus` sem estreitar: status desconhecido virava badge em branco na tela.                                                                                  |

**Estrutura nova:** `tsconfig.app.json` (o build) exclui os testes;
`npm run typecheck` (`tsconfig.test.json`) cobre `src` + `e2e` + backend. O
deploy ganhou um passo `npx tsc -b` **antes** do `vite build`.

Separar os dois é o que impede uma dívida de tipagem de mock bloquear um deploy —
e o que impede essa dívida de voltar a esconder erro de produção. Restam ~99
erros de tipo em arquivos de teste (mocks do `apiRequest` sem o campo `status`);
estão registrados no TODO como dívida, com `npm run typecheck` para medi-la.

### 🔴 `npm run lint` acusava 99 erros

Todos vinham de `server/api/dist/` — saída do `tsc` da API, gitignorada, que o
`globalIgnores(['dist'])` não pegava (o padrão sem barra só casava o `dist` da
raiz). Efeito prático: quem rodava `npm run lint` via 99 erros que não podia
consertar e aprendia a ignorar a saída. Um erro real se esconderia ali sem
esforço nenhum.

`'dist'` → `'**/dist'`. **0 erros** agora (17 warnings pré-existentes de
`react-refresh`).

## 4. Layout

### 🔴 O service worker baixava 11,2 MB na primeira visita

`globPatterns` incluía `jpg`, então as **35 fotos do evento** em
`public/eventos/kpop-night/` entravam no precache do PWA — baixadas em segundo
plano por todo visitante, no 4G de quem só queria ver um produto.

| Métrica  | Antes      | Depois        |
| -------- | ---------- | ------------- |
| Entradas | 184        | 148           |
| Precache | 11.205 KiB | **2.335 KiB** |

As fotos passaram a `runtimeCaching` (`StaleWhileRevalidate`, teto de 120
entradas / 30 dias): são cacheadas quando a tela **pede**, não antes. Foto é
conteúdo, não casca do app.

### `ProductModal` — 2297 linhas em rolagem única

A dívida nº 1 do TODO, e a causa de "a Laura não achou o campo de vídeo" no
checkup de 15/08: o bloco de vídeo ficava no terço final de ~1100 linhas de campo
numa rolagem só. Não era bug — era o formulário.

Agora são 4 abas: **Básico** · **Categorias e envio** · **Fotos e vídeos** ·
**Variações**.

Três decisões que fazem a diferença entre resolver e trocar de problema:

| Decisão                                       | Por quê                                                                                                                                                                                       |
| --------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Painéis **montados**, escondidos com `hidden` | O `handleSubmit` lê estado, não DOM, e nenhum campo usa `required` nativo. Trocar de aba não muda nada do que é salvo, e o rascunho digitado numa aba sobrevive ao Salvar disparado de outra. |
| **Contador** no rótulo da aba                 | Sem ele, aba só troca um problema de descoberta por outro. "Fotos e vídeos 4" mostra que há conteúdo lá sem precisar entrar. Conta o confirmado **e** o rascunho — o rascunho entra no save.  |
| Erro de validação **troca de aba**            | "Preço inválido na variação X" não ajuda quem está olhando a aba Básico. O helper `fail(aba, msg)` leva junto.                                                                                |

Cobertura: 6 testes novos em `ProductModal.test.tsx`, incluindo o caso que
importa — digitar o link do vídeo na aba Mídia, voltar ao Básico, salvar de lá, e
o vídeo estar no payload. Os 15 testes que já existiam passaram **sem alteração**,
o que confirma que a refatoração é neutra em comportamento.

Os E2E foram atualizados junto (`admin-shop-flows` passo 1 e 3b,
`tutorial-capture`): painel escondido é `display:none`, e o Playwright precisa
abrir a aba antes de tocar no campo — exatamente como a Laura.

## 5b. Varredura do padrão "altura chutada" (16/08, tarde)

Depois de corrigir o banner do site institucional, varri os dois repos atrás do
mesmo padrão: **elemento `fixed`/`sticky` cuja folga é chutada em vez de
medida**. A ferramenta foi `document.elementFromPoint` no centro de cada
controle, a 360/390/414/768/1024/1440px, com e sem rolagem.

### 🔴 Loja — banner cobria o header inteiro

Pior que o caso da home. O `EventAnnouncementBanner` da loja era
`sticky top-0 z-50` e o `ShopHeader` é `sticky top-0 z-40`: os dois grudavam no
**mesmo** `top: 0` e o banner vencia no z-index.

| Largura | Sobreposição | Controles bloqueados                        |
| ------- | ------------ | ------------------------------------------- |
| 360px   | 111px        | carrinho, login, busca, tema, atacado, logo |
| 390px   | 111px        | idem                                        |
| 768px   | 62px         | idem + links Loja/Atacado/Evento            |
| 1440px  | 49px         | idem                                        |

**Em todas as larguras, inclusive desktop.** Bastava rolar a página para perder
o header inteiro. Corrigido tirando o banner do `sticky`: no fluxo normal ele
ocupa espaço, rola para fora, e o header assume o `top: 0` sozinho.

Junto saiu a `--shop-event-banner-h`, que publicava `44px`/`72px` fixos e
**nenhum arquivo lia** — resíduo de um desenho (fixed + offset) trocado por
outro (sticky) sem limpar o primeiro.

### 🔴 Aviso de offline cobria a primeira linha do header

`OfflineBanner` era `fixed top-0 z-[9999]`, e as três SPAs põem cabeçalho em
`top: 0` (loja e membro por `sticky`, admin por `fixed`). Com a página rolada,
a faixa de 39px bloqueava carrinho, login, busca e tema **enquanto a conexão
estivesse caída**. Movido para o rodapé, com z abaixo do `CookieConsent`.

### ✅ O que passou

| Verificação                                      | Resultado                               |
| ------------------------------------------------ | --------------------------------------- |
| `sticky lg:top-20` (resumo do carrinho/checkout) | 80px de folga sobre header de 65px — ok |
| Rolagem horizontal, todas as larguras            | nenhuma                                 |
| Barra do admin (`fixed top-0`)                   | conteúdo compensa; sem bloqueio         |
| Modais (`fixed inset-0`)                         | overlay intencional                     |
| `CookieConsent` sobre CTAs                       | overlay esperado, some ao aceitar       |

### A regra que ficou

**Elemento que cobre outro precisa medir, não estimar** — e dois `sticky` no
mesmo `top` sempre brigam, ganhando quem tiver z maior. Quando der para deixar
no fluxo normal, deixe: aí não há folga a calcular.
